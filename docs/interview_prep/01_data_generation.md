# Interview Prep: Synthetic Data Generation

**1. Why generate synthetic data instead of using a public clinical trial dataset?**
Public trial datasets (e.g. from clinicaltrials.gov results, or de-identified EHR samples) rarely include the full combination this project needed: structured labs + adverse events + free-text investigator notes + ground-truth labels for NLP training, all linkable at the patient/visit level. Generating the data myself let me control the underlying signal (a real, non-trivial treatment effect and adverse-event burden) while guaranteeing every downstream statistical test and ML model has real ground truth to be evaluated against — including deliberately imperfect ground truth (manual CRF under-reporting) so the NLP-vs-manual-coding business metric is genuine rather than circular.

**2. How did you make sure the "effect" in your data wasn't just hardcoded to produce good-looking results?**
The treatment effect is generated from a per-patient latent "responsiveness" draw (`src/data_generation/generate_visits.py`) following a saturating dose-response curve — each patient's HbA1c/BP/LDL improvement is a random variable, not a fixed constant. The population-level difference (e.g. Drug X averaging 60.05 vs Placebo 52.15 on the primary outcome) emerges from aggregating 250 individually-randomized patients per arm, the same way it would in a real RCT. This is also why the clustering step finds genuine patient heterogeneity — "High Responders" vs "Non-Responders" reflects the same underlying random responsiveness draws.

**3. Your NLP classifier initially hit 100% accuracy — what did that tell you, and what did you do about it?**
100% accuracy on a classification task is a red flag, not a win — it almost always means the model found a trivial shortcut rather than learning real signal. In my case, the note-generation templates had a 1:1 deterministic mapping between severity keyword and label (e.g. the word "severe" always meant "Severe AE"). I fixed this by introducing controlled ambiguity: 15% of notes are written at a different severity level than the adjudicated structured grade (`_perturb_text_severity`), representing a real phenomenon — free-text language and structured CTCAE-style grading don't always agree. That dropped accuracy to a realistic 92.2%, F1-macro 0.851, with the errors concentrated exactly where you'd expect (the ambiguous cases).

**4. How did you simulate the "NLP catches more than manual coding" story without it being circular?**
I generate two separate labels per note: `true_ae_class` (the adjudicated, ground-truth severity used to write the note text and used as the ML training target) and `manually_coded_ae` (a noisy version simulating a human coder's real-world under-reporting — 25% of true Mild AEs and up to 10% of true Severe AEs get downgraded or missed, per `_apply_manual_coding_noise`). The classifier is trained against the adjudicated label, so when I compare its predictions against the noisy manual-coding field, the uplift (79.5% more detections, 100% recovery of the 19 manually-missed cases) is a genuine measurement of recovering a signal the manual process independently missed — not the model just re-deriving its own training target.

**5. What would change if this were real patient data instead of synthetic?**
Three things: (1) I couldn't control the ground truth, so validating the NLP classifier would require a gold-standard adjudicated subset labeled by medical monitors, not just trusting the CRF; (2) missing data and irregular visit schedules would be the norm rather than the exception, requiring more defensive handling than my clean 6-visits-per-patient structure; (3) I'd need a real de-identification/PHI pipeline before any of this NLP work could touch the notes at all — which is itself a meaningful part of a Life Sciences data engineering role.
