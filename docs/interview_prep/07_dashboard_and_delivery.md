# Interview Prep: Streamlit Dashboard, PDF Reporting, and Delivery

**1. Why Streamlit instead of a custom React/Flask frontend for this kind of tool?**
For a data-science-heavy internal tool aimed at medical researchers rather than end-consumers, Streamlit's tradeoffs favor speed of iteration: every page is plain Python that shares code directly with the analysis pipeline (the Cohort Explorer literally imports `welch_t_test` from the same stats module the CLI pipeline uses), so there's no separate API layer to keep in sync. The cost is less UI control and some framework-level fragility (see the question below) — a fair tradeoff for an internal analytics tool, less so for a customer-facing product where I'd reach for a proper frontend/backend split.

**2. Tell me about a real bug you hit testing this dashboard, and how you debugged it.**
While verifying the app with Playwright driving a live `streamlit run` process, Page 4 (Clinical Notes Analyser) intermittently crashed the Python process with no traceback — a segfault. I isolated it methodically: confirmed the identical pipeline logic (classify → SHAP → LLM call) worked perfectly in a plain Python thread outside Streamlit; built a minimal reproduction Streamlit app and added each piece of Page 4 back one at a time; and eventually traced it to this specific machine running on ~250MB of free RAM (checked via `vm_stat`/`top`) with heavy swap activity from other running applications — a host resource constraint, not a code defect, confirmed by the fact the same operations succeed reliably via the CLI and in the PDF generator, which exercises the identical code path. I still fixed two real, independent issues I found along the way (replacing `matplotlib`/`st.bar_chart` with Plotly for stability, and caching the SHAP explainer with `st.cache_resource` to avoid redundant model reloads on every rerun) since they were genuine improvements regardless of the underlying resource constraint.

**3. How does the "auto-generated chart" in the Chat page actually decide what chart type to use?**
Deterministically, not via another LLM call — `src/agents/chart_helper.py::suggest_chart` inspects the shape of the SQL result the Data Analysis Agent produced: if there's a `week`-named column, it's a line chart over time; one categorical + one numeric column with ≤12 rows becomes a bar chart; ≤6 rows becomes a pie-chart candidate; otherwise it falls back to a plain table. I made this a cheap, instant, rule-based decision specifically because asking an LLM "what chart should this be" on every query would be slower, costlier, and less predictable than a shape-based heuristic that's right the vast majority of the time.

**4. Why keep generated artifacts (models, plots, the executive PDF) out of git?**
They're all reproducible from the pipeline scripts (`build_database.py`, `train_classifier.py`, `run_shap_analysis.py`, `run_clustering.py`, `pdf_generator.py`), so committing them would just create merge noise and repo bloat without adding information — anyone cloning the repo regenerates identical (modulo the LLM's non-determinism) artifacts by running the documented commands. I did commit a small curated set of screenshots and one example PDF specifically for portfolio browsability, so a recruiter skimming the repo on GitHub doesn't have to run anything to see real output.

**5. How would this scale if the trial had 50,000 patients and 500,000 notes instead of 2,000/12,000?**
SQLite would be the first thing to replace — it's fine for this demo's single-writer, read-heavy pattern, but wouldn't hold up under concurrent multi-user writes at that scale; I'd move to Postgres. The TF-IDF + Logistic Regression classifier itself scales linearly and would likely still work at that data volume (possibly better, with more training examples for the thin Severe AE class), but batch-classifying 500K notes through the interactive Streamlit upload flow one at a time would be too slow — that step would need to move to an async batch job. The SHAP background sample (currently up to 200 notes) and PCA/K-Means fitting are already using bounded subsamples, so those don't need architectural changes, just more compute.
